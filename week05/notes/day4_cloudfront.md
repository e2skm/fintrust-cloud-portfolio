## Activity 176 Debrief - Route 53 Failover

### What Happened
In the Route 53 Failover lab:
1. A health check monitored the primary endpoint.
2. Route 53 polled the endpoint every 30 seconds.
3. When the web server stopped, three consecutive health check failures occurred.
4. The primary record was marked unhealthy.
5. Route 53 began returning the secondary record.
6. Traffic failed over to the secondary destination.

### Timeline
| Step | Result | Purpose |
|------|--------|---------|
| Health check created | Route 53 polls every 30s | Detect failures |
| Web server stopped | Three failed checks | Triggers unhealthy state |
| Primary unhealthy | Route 53 stops returning primary | Initiates failover |
| Secondary served | DNS resolves to secondary endpoint | Business continuity |
| Server restored | Health checks pass again | Allows failback |

### Important TTL Consideration
- A TTL of 300 seconds can significantly delay failover.
- Recommended TTL for disaster recovery records is 60 seconds or lower.
- Actual failover time is influenced by both health check failure detection and DNS cache expiration.

### Exam Notes
Keywords commonly associated with Route 53 Failover:
- Automatic failover
- Active-passive architecture
- Health check triggered redirect
- Disaster recovery DNS cutover

A Route 53 Failover configuration requires a health check to function correctly.

## Lab: CloudFront Distribution with OAC

### Business Scenario
FinTrust hosts a static customer portal in Amazon S3. Security requirements include:
1. Blocking public access to the bucket.
2. Enforcing HTTPS access through CloudFront.
3. Allowing CloudFront to authenticate to S3 using Origin Access Control (OAC).

### Lab Steps

#### 1. Create a Private S3 Bucket
- Create bucket: `fintrust-portal-assets-[your-name]`
- Region: `af-south-1`
- Enable **Block All Public Access**.
- Upload `index.html`.
- Verify direct access results in **Access Denied**.

#### 2. Create CloudFront Distribution
- Select the S3 bucket as the origin.
- Use **Origin Access Control (OAC)**.
- Enable request signing.
- Configure Viewer Protocol Policy:
  - Redirect HTTP to HTTPS.
- Set default root object:
  - `index.html`

#### 3. Apply Bucket Policy
- Copy the policy generated by CloudFront.
- Paste it into the S3 bucket policy.
- Save changes.

This allows only the CloudFront distribution to access the bucket.

#### 4. Test Deployment
- Wait for distribution deployment.
- Access the CloudFront domain name.
- Confirm `index.html` loads successfully.
- Confirm direct S3 object access still returns **Access Denied**.

#### 5. Create API Cache Behaviour
- Path pattern: `/api/*`
- Compression: Enabled
- Cache Policy: `CachingDisabled`

This prevents API responses from being cached while static assets remain cacheable.

### Lab Checkpoints
- Private S3 bucket created.
- CloudFront distribution created.
- OAC configured.
- S3 bucket policy updated.
- CloudFront successfully serves content.
- Direct S3 access blocked.
- `/api/*` behaviour configured.

## OAC vs OAI

### Origin Access Control (OAC)
- Current AWS recommended solution.
- Supports AWS KMS encrypted S3 buckets.
- Uses request signing.
- Provides improved security and flexibility.

### Origin Access Identity (OAI)
- Older CloudFront-to-S3 access mechanism.
- Being phased out in favour of OAC.
- Does not support newer capabilities available with OAC.

### Why OAC Is Preferred
- Better security.
- Modern AWS standard.
- KMS support.
- Enhanced request signing capabilities.

## Reflection Questions

### 1. Why is OAC preferred over OAI?
OAC provides stronger security, supports KMS encryption, and uses the modern CloudFront request-signing model.

### 2. When would CloudFront be used in front of an ALB?
When dynamic applications require global content acceleration, caching, DDoS protection, and reduced latency while still routing requests to backend services through an Application Load Balancer.

### 3. How do you immediately deliver an urgent CSS fix if TTL is one day?
Use a CloudFront cache invalidation so users receive the updated file immediately rather than waiting for cache expiration.
